# ADR 0025 — The `apeCAD.section-draft` v1 contract

**Status:** Accepted (2026-10-14). Proposed 2026-10-09; accepted by the owner on 2026-10-14

Plan number 0021 (see the numbering table in [ADR 0024](0024-section-mode-rc-intent.md)).
Builds on ADR 0024 (section mode) and [ADR 0006](0006-one-source-of-truth.md) (one writer).

## Context

Three repos must agree on one JSON text:

- apeCAD writes it.
- apeConcrete reads it (`io/apecad.section_from_apecad`, its ADR-0025 D8).
- ape-web-tools stores it in a run and hands it to apeConcrete (its ADR-0006 D4).

Before the plan, apeCAD and apeConcrete had drafted two different schemas (plan §7, issue
1). The plan settled one text (§4.1) and assigned it to apeCAD as its single home (P1).
apeConcrete ADR-0025 D8 and ape-web-tools ADR-0006 D4 both wait on this record to paste it.

A draft is kept for years inside recorded runs, so it must reopen even after apeCAD's
geometry code changes (P9).

## Decision

1. **The contract text lives in [`specs/section-draft.md`](../specs/section-draft.md).** That
   spec holds the plan's §4.1 block byte for byte, with its SHA-256, and states its rules
   field by field. apeConcrete ADR-0025 D8 and ape-web-tools ADR-0006 paste that block. A copy
   whose SHA-256 differs is not the contract.
2. **A draft has two parts with different jobs:**
   - `document` is the full apeCAD ops log (`apeCAD.document.v1`). It is the source of truth
     (ADR 0006): apeCAD reopens a draft by replaying it.
   - `section` is a derived projection for consumers. It is a pure function of the document,
     like `to_frame()`, and never a second editor. apeConcrete reads `section` only and never
     replays ops.
3. **Reopen warns on numbers and refuses on structure (P9).**
   `document_from_draft(draft) -> (Document, warnings)` replays `document` and recomputes
   `section`:
   - A numeric difference against the stored block (rel_tol 1e-9) is a warning.
   - A structural difference is refused: an id that is missing or extra, a different kind, or
     a different hoop membership.
   - An unknown `schema` or `version` is refused.
4. **Strict hull, legs with steel, closed vocabulary.** These are ADR 0024's P2, P4 and P12
   carried into the JSON:
   - `hoops[].bar_ids` is the strict CCW hull.
   - `wall_legs[].horizontal` is present, or null.
   - Every `designation` is from the vocabulary.
   - Every `diameter_mm` matches its designation. apeConcrete trusts the designation and
     refuses a mismatch.
5. **Provenance (P13).** `producer = {apeCAD_version, apeCAD_commit or null}`. apeCAD's
   version moves from 0.0.0 to **0.1.0** in the change that first writes a section-draft v1.
6. **Versioning rule.** An optional field added is additive and keeps `version` 1. A changed
   meaning bumps `version`. `warnings` is advisory: consumers may show it, and must not gate on
   it.
7. **The seed is the way back.** `apeCAD.section-seed` v1 is the same `section` block with list
   indices in place of ids. apeConcrete emits it from a declared or DXF section, and apeCAD
   alone turns it into ops (plan stage C10). No other repo writes apeCAD ops.
8. **Constants and fixtures in apeCAD:**

   | Constant | Value | Home (ADR 0023 layout) |
   |---|---|---|
   | `DRAFT_SCHEMA`, `DRAFT_SCHEMA_VERSION` | `"apeCAD.section-draft"`, `1` | `apeCAD/section/draft.py` |
   | `SEED_SCHEMA`, `SEED_SCHEMA_VERSION` | `"apeCAD.section-seed"`, `1` | `apeCAD/section/seed.py` |
   | `DESIGNATIONS` | the ADR 0024 vocabulary | `apeCAD/section/designations.py` |
   | `SCHEMA_ID`, `SUPPORTED_SCHEMA_IDS` | `apeCAD.document.v1`; reads v0 and v1 | `apeCAD/ops/types.py` |

   The plan's §4.2 names `section_draft.py` and `section_designations.py` at the package root.
   The constant names are the contract, and the module paths follow ADR 0023.

   Fixtures live in `tests/fixtures/section_draft/`: `rect_boundary_hoops`,
   `l_wall_two_hoops`, `c_wall_crossties` and `inclined_outline`. They are generated by a
   script and compared at rel 1e-12. The rect fixture reproduces apeConcrete's
   `rect_300x3000`: 18 boundary bars, hoop Ø10, clear cover 25. apeConcrete copies the
   fixtures at a pinned apeCAD sha (its stage A11).

## Alternatives rejected

| Rejected | Why |
|---|---|
| The ops log alone, with consumers replaying it | Every consumer would need apeCAD's replay semantics, and apeConcrete must not import apeCAD (O5) |
| The `section` block alone | Loses the drawing's history. A draft could no longer reopen as an editable document (O6) |
| Refuse any numeric difference on reopen | A geometry fix of 1 ulp would lock a years-old run out (plan §7, issue 8) |
| Contract text in each repo's ADR, kept in step by hand | Two texts already diverged once. One home plus a hash makes drift visible |
| apeConcrete writes apeCAD ops for older sections | Two writers of one log (ADR 0006). The seed is data, and apeCAD alone writes ops |

## Consequences

- apeConcrete ADR-0025 D8 and ape-web-tools ADR-0006 D4 can be completed by pasting the spec
  block once this record is accepted.
- Any edit to the fenced block changes its SHA-256. The edit is either additive (rule 6, with
  the block and hash re-published to both consumers in the same round) or a version bump.
- The fixtures become the gated cross-repo test: apeConcrete's reader runs against committed
  copies, not against a live apeCAD.
- Implementation is plan stage C4 (draft, fixtures, version) and C10 (seed reader).
